Model Context Protocol：模型上下文协议。是一种为了让大模型能够更好地了解和选择工具的协议。

但是MCP协议并没有作用到大模型的通信中，而是作用于MCP Server和MCP Client之间。

MCP有几个核心组件：MCP Host、MCP Server、MCP Client

1 三大组件

1.1 MCP Host

MCP Host是一种支持MCP协议的软件，是MCP Client的宿主。例如VS Code中的插件Cline，或者是Cursor、Claude Code、Cherry Studio等等。

1.2 MCP Client

MCP Client一般都在MCP Host中实现，MCP Client是为了和MCP Server通信而生，MCP协议真正作用的地方就在于MCP Client和MCP Server的通信之间。

  • MCP Client：专注于和MCP Server的对话，使用MCP协议进行通信
  • MCP Host：更像是一个将各大模块的协调者，它需要协调整合整个对话过程，从用户提出任务到中间MCP Client和MCP Server的对话，再到最终大模型的返回结果。

1.3 MCP Server

MCP Server和传统的Server并不一样，MCP Server是一种软件，只是在里面可能也会提供网络通信或者是本地命令的执行等等。

市面上大部分的MCP Server都是使用NodeJs或Python实现的。

大部分的MCP Server都要求联网，因为需要去获取外部的信息，当然也有一些并不需要联网，因为只要进行本地操作，需要去执行本地的命令等。

MCP Server可以在MCP Host的商城（如果该Host有自己实现商城）下载，也可以到一些商城下载：

  • https://mcp.so/zh
  • https://mcpmarket.com/zh
  • https://smithery.ai/

等等。

这里以开发一个“weather”服务为例。

uv init weather
cd weather
uv venv   # 打开虚拟环境
source .venv/Script/activate  # 进入虚拟环境
uv add "mcp[cli]" httpx

2.1 MCP Server要点

在MCP Server中，要创建一个tool，主要需要实现4点：

  1. 使用注解@mcp.tool()来表示该函数要注册为工具
  2. 使用可读性的名称作为标题，最好可以从函数名看出该函数的作用
  3. 明确该函数的入参及入参类型
  4. 在函数中，使用doc注释（3引号）来描述该工具的作用以及调用时机

一个工具的创建，需要包含的内容其实就是Function-Calling所需的内容，因为在发送给大模型的时候，其实也是将这个工具函数的信息转换为对应大模型通信协议的Function-Calling。

到这里，准备动作就已经结束了，MCP Host也已经知道MCP Server具备的工具列表，并且也维护了MCP Server的状态。

3.2.4 工具调用

当用户发起问题时，MCP Host会将问题和工具清单发送给大模型，由大模型来选择要执行的工具。

此时就涉及到MCP Host如果通知MCP Server调用对应工具来获取答案。

这里MCP Host会发送调用请求给MCP Server，即method为“tools/call”，例如上图，在params中声明要调用的函数名以及该函数的入参，这里的入参要严格按照在准备阶段由MCP Server提供的工具清单里面的inputSchema来设置。

之后MCP Server就会通过Http去调用外部接口，或者执行指令等等。

3.3 重点解释准备阶段

首先MCP Host感知MCP Server的存在，是由我们手动去配置文件，将MCP Server配置到MCP Host里面的。

3.3.1 启动MCP Server

在MCP Host，例如Cline中，通过点击MCP Servers列表中的“重新连接”按钮，MCP Client就会在后台拉起一个MCP Server服务进程。

3.3.2 发送请求

等待MCP Server启动成功后，MCP Client会发送一个获取工具列表的请求，方法名为"tools/list"

3.3.3 返回工具清单

接收到请求之后，MCP Server就会将自身具有的所有工具，按照Json Schema的形式封装后返回给MCP Client

3.3.4 解析

MCP Client接收到返回后，会去解析里面的tools，并翻译为对应大模型的协议格式，等待下次向大模型发起询问的时候，将tools拼接在给大模型的System Prompt中。

4 MCP Host与大模型的交互

在我们写一个服务器脚本，拦截MCP Host与大模型之间的通信信息，我们在这些信息中，可以清晰地看到MCP Host在向大模型发送询问请求时，会同时设置好SystemPrompt：

{
   "role": "system",
   "content": "..."
}

其中content就是Cline为大模型的回答做好的规范要求。content的内容相当长，可以看"AI概念杂记"中的"Cline向大模型发送System Prompt.md"笔记。

其中有几个点需要注意的：

4.1 工具使用格式

规定了大模型选择好工具后，对要调用的工具的格式，需要采用xml的风格。Cline自己设定了一套XML规则：工具名称作为开始和结束标签，参数包含在标签中：

<read-file>
    <path>main.py</path>
</read-file>

4.2 工具

在第二部分内容中的工具列表指的是Cline自定义的工具，例如：

  • execute_command：执行本地命令
  • read_file：读取文件
  • write_to_file：将内容写入文件中
  • use_mcp_tool：需要调用的tool信息
  • attempt_completion：调用工具结束，大模型会把最终结论放到attempt_completion的result标签中
  • ...

4.3 工具使用示例

提供给大模型的一些工具使用示例。

4.4 工具使用指南

大模型在选择工具时，需要遵守的一些规范，例如每次在给出选择或给出结论之前，都要进行thinking等等。

4.5 已连接的MCP Server

在这里将所有MCP Server的工具解析后，将这些工具的信息发送给大模型，大模型在判断选择哪个工具时，都是从这个工具清单中选择。

4.6 其他的事项

5 大模型的返回

大模型返回时，一般都是采用SSE流式返回。即一个一个token返回。

5.1 开头的注释

在大模型还没有得出结论时，为了不让客户端以为超时而断开连接，大模型会先一直返回注释信息

:DeepSeek Processing

这个注释以":"开头，后面的内容是什么无所谓，只是让客户端感知到这个连接一直存在即可。

5.2 真实数据

data: {...}

真实数据以"data"开头，后面的大括号（json）即是大模型要返回的内容，json数据中有个content属性，这个content属性的值便是大模型对这个任务或问题的回答，当然，大模型会不断发送data真实数据，我们需要将content的内容拼接起来，才是最终的结论数据。

5.3 大模型的多次思考

例如MCP Host，第一次发送给大模型是为了让大模型能够选择要执行的工具，在MCP Host执行完工具逻辑后，需要将工具得到的结果再次发送给大模型。

那么在第二次发送给大模型的时候，还是需要将第一次的信息，包括初始问题和第一次大模型的返回，打包一起发送给大模型。

因为大模型是无记忆的。

6 大模型的状态

在整个MCP的调用链中，大模型一直处于三种状态：思考、行动、观察

6.1 思考

对于MCP Host发来的问题或任务进行思考，例如应该选择哪个工具，该工具的参数是什么，或者是否已经能够回答该问题

6.2 行动

根据MCP Host的格式要求和回答规范，封装返回的内容，并发送给MCP Host

6.3 观察

对于MCP Host发送过来的工具调用结果进行观察，看看是否已经足够回答问题，如果还需要继续执行，则再次进入思考状态

7 ReAct

ReAct的基本思想就是：Thought、Action、Observation

ReAct只是一种思想，并没有规范其实现者需要使用什么协议来完成，例如Cline采用了XML格式来实现ReAct思想。我们也可以使用json，甚至是纯文本。
