## 1. 模块概述

笔记模块是 AI Manager 的核心功能之一，为用户提供**多层文件夹 + 笔记 + 标签**的内容管理能力。

### 1.1 核心能力矩阵

| 能力 | 说明 | 实现状态 |
|------|------|----------|
| 多级文件夹（笔记本） | 支持无限层级嵌套的文件夹树 | ✅ 已实现 |
| 富文本笔记 | 基于 @wangeditor 的 HTML 富文本编辑 | ✅ 已实现 |
| Markdown 笔记 | 标题以 `.md` 结尾时自动切换 MD 模式 | ✅ 已实现 |
| 标签系统 | 多对多标签关联，支持标签管理和快速筛选 | ✅ 已实现 |
| 置顶/收藏 | 笔记和文件夹均可置顶和收藏 | ✅ 已实现 |
| 搜索 | 标题和正文摘录模糊搜索 | ✅ 已实现 |
| 回收站 | 逻辑删除 + 物理清除 | ✅ 已实现 |
| 百度网盘同步 | 双写策略，本地 + 云盘冗余存储 | ✅ 已实现 |
| 版本仲裁 | 本地 vs 云盘的版本冲突解决 | ✅ 已实现 |
| 定时差值同步 | 每5分钟自动同步未上传笔记 | ✅ 已实现 |
| 导出 Word | 将笔记导出为 .docx 文件 | ✅ 已实现 |
| 目录导航 | 自动提取文章标题结构生成 TOC | ✅ 已实现 |

### 2.2 架构分层详解

| 层级 | 技术 | 职责 |
|------|------|------|
| **表现层** (PC) | Vue 3 + Element Plus + @wangeditor | 树形文件夹导航、笔记编辑器、目录、标签管理 |
| **表现层** (移动) | Vue 3 + 自研移动组件 (v1/v2) | 移动端适配的笔记浏览和编辑 |
| **API 层** | Axios + RESTful | 前端所有 API 调用封装在 `api/notebook.ts` |
| **Controller** | Spring Boot REST | 参数校验、路由分发 `@RequestMapping("/api/notes")` |
| **Service** | Spring Boot @Service | 业务逻辑、事务管理、跨服务调用 |
| **Storage 接口** | 策略模式 + Spring DI | 内容存储抽象，支持多种存储后端插拔 |
| **Mapper** | MyBatis-Plus | CRUD + 分页 + 逻辑删除 |
| **数据层** | MySQL 8 + Redis 7 + 百度网盘 | 元数据持久化、内容缓存、云备份 |

### 2.3 中间件使用

| 中间件 | 用途 | 配置 | 备注 |
|--------|------|------|------|
| **MySQL 8** | 笔记/文件夹/标签的元数据持久化 | `jdbc:mysql://localhost:3306/ai_manager_admin` | 核心数据存储 |
| **Redis 7** | 笔记正文缓存 (prefix: `nb:content:`) | TTL=3600s, Max=512MB | 读加速、编辑时暂存 |
| **百度网盘 API** | 笔记正文云备份 | OAuth2 授权, 目录 `/apps/ai_blog/` | 第三方存储，有调用频率限制 |
| **SSH (SSHJ)** | 远程部署（非笔记模块直接使用） | - | 部署管线 |

### 2.4 未使用的中间件

| 中间件 | 说明 | 为什么未使用 |
|--------|------|-------------|
| **消息队列 (RabbitMQ/Kafka)** | 异步任务调度 | 当前用 `CompletableFuture.runAsync()` 处理同步，适合当前规模 |
| **WebSocket** | 实时推送 | 用 SSE (Server-Sent Events) 替代 |
| **ElasticSearch** | 全文搜索 | 使用 MySQL LIKE 模糊搜索，性能瓶颈明显 |
| **对象存储 (OSS/S3)** | 文件存储 | 使用本地文件系统 + 百度网盘替代 |

### 3.3 SQL 建表要点

- 所有表使用 `utf8mb4` + `utf8mb4_unicode_ci` 字符集
- 主键使用 `AUTO_INCREMENT` BIGINT
- 逻辑删除使用 `@TableLogic` MyBatis-Plus 注解
- 索引建议缺少：`nb_note.content_excerpt` 搜索无索引
- `nb_note_tag_rel` 无联合唯一约束，可能导致重复关联

## 4. 存储架构解析

### 4.1 存储策略模式

笔记正文存储采用了**策略模式**，核心接口为 `NoteContentStorage`：

```java
public interface NoteContentStorage {
    String type();                          // 存储类型标识
    NoteContentSaveResult save(Ref, String); // 保存
    String load(Ref);                        // 加载
    void delete(Ref);                        // 删除
    void ensureRoot();                       // 初始化根目录
}
```

### 4.2 三种存储实现

| 实现类 | type() | 说明 | 优势 | 劣势 |
|--------|--------|------|------|------|
| `LocalFileNoteContentStorage` | `LOCAL` | 本地文件系统 `uploads/notebook-content/notes/{id}.html` | 速度快，无网络依赖 | 无备份，硬盘损坏则丢失 |
| `BaiduPanNoteContentStorage` | `BAIDU_PAN` | 百度网盘 `/apps/ai_blog/notes/{id}.html` | 云端备份，跨设备 | 有 API 频率限制，依赖网络，有 OAuth 授权门槛 |
| `DualWriteNoteContentStorage` | `DUAL` | 同时写本地 + 云盘 | 冗余备份，云盘失败自动降级 | 写放大（双倍 I/O），复杂度高 |

### 4.3 双写策略（核心机制）

**DualWrite** 是默认的存储策略，工作流程如下：

```
用户编辑保存
      │
      ▼
┌─────────────────────┐
│  1. Redis 缓存写入  │  ← 快速返回，用户体验好
│  (TTL=3600s)        │
└─────────┬───────────┘
          │
          ▼  (异步后台)
┌─────────────────────┐
│  2. 双写保存        │
│  ┌───────────────┐  │
│  │ 本地文件写入   │──│── 必须成功，否则抛异常
│  └───────┬───────┘  │
│          ▼          │
│  ┌───────────────┐  │
│  │ 云盘上传      │──│── 失败时降级，设 CLOUD_PENDING
│  └───────────────┘  │
└─────────────────────┘
          │
          ▼
┌─────────────────────┐
│  3. 版本元数据写入  │  ← 写入 .meta.json（本地+云盘）
│  (version + hash)   │
└─────────────────────┘
```

### 4.4 版本仲裁

当本地和云盘内容不一致时，通过 `NoteContentVersionServiceImpl.pickWinner()` 决定以谁为准：

1. **版本号比较**：version 大者胜出
2. **时间戳比较**：version 相同时，updatedAt 较新者胜出
3. **回填机制**：云盘胜出时，将云盘内容回填到本地；本地胜出时，标记 CLOUD_PENDING 待上传

### 4.5 差值同步机制

- **启动时**：`NoteContentReconcileRunner` 执行全量差值同步
- **定时**：`NoteContentReconcileJob` 每 5 分钟执行一次
- **按需**：用户打开笔记时触发单条差值同步
- **并发控制**：`noteLocks` ConcurrentHashMap + `reconcileRunning` AtomicBoolean 防止重复执行

### 7.2 保存策略

| 策略 | 触发时机 | 方法 | 特点 |
|------|----------|------|------|

## 8. 弊端分析

### 8.1 架构层面

#### 8.1.1 高 🔴 全量树加载性能问题

**问题描述**：`GET /api/notebooks/tree` 每次加载全部文件夹和笔记的完整数据，生成全量树结构。随着笔记数量增长（>1000条），响应时间线性增长，前端渲染卡顿。

**代码路径**：[NbNotebookServiceImpl.java](file:///g:\projects\ai_project\ai_manager\admin-backend\admin-system\src\main\java\com\ai\manager\system\service\impl\NbNotebookServiceImpl.java#L37-L52)

```java
// 每次加载全部数据
List<NbNotebook> notebooks = list(new LambdaQueryWrapper<NbNotebook>()
    .orderByAsc(NbNotebook::getSortOrder)
    .orderByAsc(NbNotebook::getId));
List<NbNote> notes = nbNoteMapper.selectList(new LambdaQueryWrapper<NbNote>()
    .orderByDesc(NbNote::getIsPinned)
    .orderByAsc(NbNote::getSortOrder)
    .orderByAsc(NbNote::getId));
```

#### 8.1.2 高 🔴 搜索性能瓶颈

**问题描述**：笔记搜索使用 MySQL LIKE 模糊匹配 `title` 和 `content_excerpt`，没有全文索引。当笔记量增大时：
- LIKE '%keyword%' 无法使用索引
- 搜索结果仅限前 50 条，使用 `LIMIT 50` 截断
- 没有高亮、分词、排序优化

**代码路径**：[NbNoteServiceImpl.java](file:///g:\projects\ai_project\ai_manager\admin-backend\admin-system\src\main\java\com\ai\manager\system\service\impl\NbNoteServiceImpl.java#L84-L96)

#### 8.1.3 高 🔴 百度网盘单点依赖

**问题描述**：
- 百度网盘 OAuth Token 有有效期，过期后云同步失败
- API 有调用频率限制（QPS），大量笔记同步时可能被限流
- 百度网盘 API 稳定性不可靠，当前代码中已有 `isBaiduApiErrorBody()` 容错
- 用户必须注册百度开放平台应用，配置门槛高

**代码路径**：[NbNoteContentServiceImpl.java](file:///g:\projects\ai_project\ai_manager\admin-backend\admin-system\src\main\java\com\ai\manager\system\service\impl\NbNoteContentServiceImpl.java#L76-L81)

```java
// 需要识别百度 API 错误响应
if (NoteContentUtils.isBaiduApiErrorBody(cached)) {
    stringRedisTemplate.delete(cacheKey);
}
```

#### 8.1.4 中 🟡 Redis 缓存容量风险

**问题描述**：笔记正文缓存上限 512MB，没有 LRU 淘汰策略的显式配置。大笔记或大量笔记可能撑爆 Redis 内存。

**代码路径**：通过 `StorageCenterService.enforceCacheLimit()` 检查，但实现效果依赖 Redis 本身的内存淘汰策略。

#### 8.1.5 中 🟡 异步同步的非事务性

**问题描述**：`stageContent()` 在事务中更新 MySQL，但 `syncContentToStorage()` 是异步 `CompletableFuture.runAsync()`。如果保存 MySQL 成功但 Redis 写入失败（或相反），会导致数据不一致。

**代码路径**：[NbNoteServiceImpl.java](file:///g:\projects\ai_project\ai_manager\admin-backend\admin-system\src\main\java\com\ai\manager\system\service\impl\NbNoteServiceImpl.java#L270-L289)

```
事务开始
  ├─ stageContent() → Redis 写入 (可能在事务外)
  ├─ updateById() → MySQL 更新
  └─ scheduleSync() → 异步执行
事务提交
```

#### 8.1.6 中 🟡 循环依赖检测性能

**问题描述**：文件夹移动时的循环依赖检测 (`isDescendant`) 使用递归逐级查询数据库，每次移动操作产生 N 次 SQL 查询。在深层嵌套时性能差。

**代码路径**：[NbNotebookServiceImpl.java](file:///g:\projects\ai_project\ai_manager\admin-backend\admin-system\src\main\java\com\ai\manager\system\service\impl\NbNotebookServiceImpl.java#L222-L235)

### 8.2 代码层面

#### 8.2.1 中 🟡 前端保存竞态

**问题描述**：`loadNoteDetail()` 使用 `noteLoadSeq` 做竞态控制，但多个保存操作（手动 + 后台 + keepalive）可能同时进行，导致版本覆盖。

**代码路径**：[NotebookView.vue](file:///g:\projects\ai_project\ai_manager\admin-web\src\views\NotebookView.vue#L1252-L1264)

#### 8.2.2 低 🟢 标签关联无唯一约束

**问题描述**：`nb_note_tag_rel` 表没有 `(note_id, tag_id)` 联合唯一约束，可能导致重复关联。

**代码路径**：当前逻辑使用全量删除重建模式（syncNoteTags 先删后插），并发下可能出现重复。

#### 8.2.3 低 🟢 前端无内容自动保存定时器

**问题描述**：前端没有定时自动保存机制（如每 30 秒自动保存），仅依赖手动保存和切换/离开时的触发。用户长时间编辑后忘记保存可能丢失内容。

### 8.3 产品功能层面

#### 8.3.1 中 🟡 无历史版本功能

- 每次编辑覆盖旧内容，无法回溯
- 用户在笔记中写代码时，旧版本没有被保留
- 对比竞品（Notion/语雀），版本回滚是核心功能之一

#### 8.3.2 中 🟡 无全文搜索

- 搜索仅匹配 `title` 和 `content_excerpt`（前200字符摘要）
- 无法搜索笔记正文全文
- 没有分词、拼音模糊搜索、搜索结果高亮

#### 8.3.3 低 🟢 无 AI 能力

- 项目名为 AI Manager，但笔记模块没有集成任何 AI 能力
- 缺少智能推荐标签、自动摘要、内容纠错、AI 写作辅助
- 缺少语义搜索（向量搜索）

## 9. 改进建议

### 9.1 高优先级

#### 建议1：引入 ElasticSearch 全文搜索

**方案**：搭建 ES 索引，替代 MySQL LIKE 搜索
- 笔记创建/更新时自动同步到 ES
- 支持分词搜索、拼音搜索、搜索结果高亮
- 支持搜索正文全文（不限 excerpt）
- 后端新增一个搜索适配层，兼容当前 `searchNotes` 接口

**复杂度**：⭐⭐⭐⭐
**收益**：⭐⭐⭐⭐⭐

#### 建议2：树结构懒加载

**方案**：改全量加载为按需懒加载
- 初始只加载根节点和展开的第一层
- 点击文件夹时才加载其子节点
- 前端使用 el-tree 的 `lazy` 模式
- 后端新增根据 parentId 查询子节点接口

**复杂度**：⭐⭐⭐
**收益**：⭐⭐⭐⭐⭐

#### 建议3：增加替代云存储

**方案**：减少对百度网盘的强依赖
- 支持 WebDAV（兼容 Nextcloud/坚果云）
- 支持 S3 协议（兼容 MinIO/阿里云OSS）
- 存储策略模式已准备好，新增实现类即可
- 配置化切换存储后端

**复杂度**：⭐⭐
**收益**：⭐⭐⭐⭐

#### 建议4：定时自动保存

**方案**：前端增加定时自动保存
- 每 30 秒检测 isDirty，自动调用后台保存
- 不影响用户手动保存的体验
- 降低编辑器内容丢失风险

**复杂度**：⭐
**收益**：⭐⭐⭐⭐

## 10. 总结

### 架构优势
- **存储策略模式**设计合理，易于扩展新存储后端
- **异步同步机制**减少用户等待时间
- **双写策略**提供了一定程度的数据冗余
- **版本仲裁机制**解决了云地冲突问题
- **前端保存策略**完善（手动/后台/keepalive/可见性变化）

### 核心痛点
1. **搜索能力弱** → 需要 ES 替代 MySQL LIKE
2. **百度网盘强依赖** → 需要替代云存储
3. **全量树加载** → 需要懒加载
4. **无 AI 能力** → 与项目名称不符
5. **无历史版本** → 功能深度不足

### 架构评分

| 维度 | 评分 | 说明 |
|------|------|------|
| 可扩展性 | ⭐⭐⭐⭐ | 策略模式、接口抽象设计合理 |
| 可用性 | ⭐⭐⭐ | 百度网盘单点故障风险 |
| 性能 | ⭐⭐⭐ | 全量加载 + LIKE 搜索瓶颈 |
| 可维护性 | ⭐⭐⭐⭐ | 代码结构清晰，注释完善 |
| 安全性 | ⭐⭐⭐ | 无 XSS、CSRF 防护评估 |
| 用户体验 | ⭐⭐⭐⭐ | 保存策略完善，编辑体验流畅 |
