## 0. 结论摘要（TL;DR）

- **平板问题根因**：壳层判定是「PC/Mobile」二分（`MOBILE_MAX_WIDTH=768`），无平板档；PC 端 `NotebookView.vue` 是三栏**固定宽度**布局（侧栏 280px + TOC 240px + 外栏 148px），在 769–1200px 中宽下内容区塌缩到 **7–262px**，与用户反馈「内容区太小、目录/统计占满界面」完全吻合。
- **修复思路**：不动壳层二分，只在 PC 壳 `NotebookView.vue` 组件内做响应式平板档（`@media` 1200/1024 两档 + `matchMedia` 运行时状态）。侧栏窄档改为**原位抽屉**（`position:absolute`），TOC 窄档默认折叠为浮动按钮，统计卡 auto-fit 压矮。**对桌面 ≥1200 与移动壳 ≤768 零回归。**
- **方案状态**：老杨审核**有条件批准**。落地顺序：常量 → P0-1（主修复）→ P0-2 → P0-3 → P1-1 → P2-2（独立提交）；P2-1 砍掉。
- **架构层面**：笔记本模块整体骨架合理（存储抽象 + 双写 + 版本对账），但存在 **2 个 P0 数据安全风险**（R1 Redis 是唯一持久点、R2 对账可能静默覆盖新内容）与 8 个中低风险，需按优先级跟进，与本次布局修复解耦、分别排期。

## 1. 模块架构全景

### 1.1 后端（admin-backend）

**三实体 + 存储抽象层**：

| 实体 | 说明 |
|---|---|
| `NbNotebook`（文件夹） | `parentId` 自引用构成树，无 DB 外键，删除由 Service 手工级联 |
| `NbNote`（笔记） | `notebookId` → 文件夹；正文**不落库**，只存 `storageType/storagePath/storageFsId/contentHash/contentSize/contentVersion/syncStatus/syncError` 等存储指针与同步状态 |
| `NbNoteTag` / `NbNoteTagRel` | 标签目录 + note↔tag 多对多，删除标签时手动清 rel |

**存储抽象层**（`service/storage/`、`domain/storage/`，本模块最亮眼的分层）：
- 存储能力接口 `NoteContentStorage`，实现：`LocalFileNoteContentStorage`（LOCAL）、`BaiduPanNoteContentStorage`（BAIDU_PAN）。
- `StorageRouter` 按配置 + 授权状态解析 `StorageChain`：双写 → `OrderedChain[本地, 网盘]`；旧版 → 单层。
- `OrderedChain`：save 先写主存储再尽力写远程；load 逐层尝试；**各存储层用 `noteId` 自建路径**（双写跑通的关键约定）。
- `NoteContentVersionService`：`.meta.json` 版本对账，双写一致性核心。
- `NbNoteContentServiceImpl`：编排 Redis 暂存 + 异步落盘 + 对账（构造注入 10 个依赖，是后端最重的服务）。
- `NoteContentSyncServiceImpl`：异步调度（`CompletableFuture.runAsync` + 每 noteId 一把锁）。
- `StorageCenterService`：全局存储治理（配额/超限策略/孤儿清理/缓存上限），跨笔记、电商、导入多 zone 复用。
- 配套：`NbNoteImageUploadService`、`NoteContentReconcileRunner`（启动对账）、`NoteContentReconcileJob`（每 5 分钟）、`NoteContentVersionService`。

### 1.2 前端：三套视图并存

| 视图 | 入口 / 路由 | 能力 | 定位 |
|---|---|---|---|
| PC | `main_pc → router/index`，`views/NotebookView.vue`（约 3200 行） | **唯一具备完整 CRUD**：新建/编辑（wangEditor 富文本 + MD 三模式）、置顶/收藏/移动/复制/删除/回收站/标签/导出 Word/目录 | 内容生产端 |
| Mobile v1 | `main_mobile → router/mobile`，`mobile/views/notebook/*` | 只读：抽屉树、置顶+文件夹卡片（手绘风）、搜索、详情 v-html | 历史手机壳（已默认停用，v2 为默认，v1 作回退通道） |
| Mobile v2 | `main_mobileV2 → router/mobile-v2`，`mobile-v2/views/notebook/*` | 只读：首页聚合（文件夹+置顶+最近）、文件夹页、详情 v-html + 自写 MD 转换器、搜索 | 现行手机壳 |

> **关键事实**：两套 mobile 端**完全没有** `updateNote/createNote/removeNote` 调用（已全局验证）——移动端是纯「浏览壳」，增删改、回收站、标签管理只在 PC 端存在。这是三视图并存格局下最实质的能力缺口。

### 1.3 壳层判定与入口

`index.html → public/app-shell.js（Vue 加载前同步判定）→ src/bootstrap.ts → 按壳层动态 import(main_pc | main_mobileV2 | main_mobile)`。

判定优先级：URL `?shell=` > sessionStorage 手动切换 > 自动识别（UA/触摸 > 视口 ≤768）。移动 UI 版本由 localStorage `mobile-ui-version` 决定，默认 v2。

### 1.4 关键数据流

- **打开笔记**：`GET /api/notes/{id}` → 先查 Redis `nb:content:{id}`；未命中走 `reconcile`（本地/云盘各读 + meta，单次冷打开 ≥2 次网盘调用）或 `resolveStorage().load()`；回写缓存（TTL 3600s）。
- **新建/编辑/保存**：`createNote`（事务）→ 若带内容 `stageContent`（**只写 Redis 缓存** + 更新 excerpt/size/sync_status=SYNCING，hash 保持旧值）→ 异步 `syncContentToStorage` 落本地 + 尽力写网盘 → 成功回写 hash/version/path/fs_id/sync_status。前端 `PUT` 同步返回，但「已保存」实际 = 「已进 Redis」而非「已落盘/上云」。PC 端用 `pagehide/visibilitychange` + `updateNoteKeepalive`（fetch keepalive）兜底。
- **回收站**：删除 = 逻辑删除（正文与网盘文件保留）；恢复 = 置 `deleted=0`；永久删除 = `purgeNote` 先删内容（本地+网盘+Redis）再清标签 rel。
- **对账**：启动 Runner + 每 5 分钟 Job → 逐条读本地/云盘两侧 + meta，四情形处理（仅本地补传云盘 / 仅云盘回填本地 / 两边不同按 `pickWinner` 版本高者胜）。

### 1.5 内容存储架构合理性评估

**做对的部分**：本地为主、网盘为远程副本的方向正确（读快、断网可读、网盘做备份与跨设备）；`OrderedChain`「每层自建路径、只认 noteId」规避跨存储路径污染；版本对账 + 差量补传是「文件系统当 DB」场景的务实兜底；存储中心统一治理跨模块复用；`updateSyncEntity` 置空 title 防异步覆盖是务实技巧。

**总体判断**：骨架合理、超过多数个人项目水准；但「以 Redis 做写缓冲 + 以 meta 文件做版本仲裁 + 无界异步」三点叠加，把数据安全押在「Redis 不丢 + meta 总是最新」两个脆弱假设上。风险随数据量与写入频率上升。

### 2.2 平板端专项（核心）

**壳层判定路径**：

| 平板情形 | 判定 | 进入的布局 |
|---|---|---|
| iPad 正常 UA（`/iPad/` 或触摸 MacIntel） | mobile | mobile-v2 |
| 安卓平板正常 UA | mobile | mobile-v2 |
| Surface / 安卓浏览器「桌面版网站」/ `?shell=pc` / 桌面窗口缩到 769–1280 | **pc** | **`NotebookView.vue`（PC 布局）** |

> 用户反馈「平板进入后内容区太小、目录/统计占满界面」与 **PC 壳平板宽度下的 `NotebookView.vue`** 完全吻合——只有它存在「目录树 + 统计 + TOC + 内容区」多栏挤压。mobile-v2 是单列卡片流，不存在该问题。

**量化数据**（宽度账本：rail 148 + 面板内边距 40 + 边框 2 = `layout` = W−190；侧栏 280 → 主区 = W−470；TOC 252 → 编辑器 = W−722；编辑器内边距 40 → **内容区 = W−762**）：

| 视口 W | 内容区（TOC 展开） | 内容区（TOC 折叠） | 侧栏占比 |
|---|---|---|---|
| 1280 | **518** | 770 | 25.7% |
| 1180 | **418** | 670 | 28.3% |
| 1024 | **262** | 514 | 33.6% |
| 900 | **138** | 390 | 39.4% |
| 834（iPad Air 竖屏） | **72** | 324 | 43.5% |
| 800 | **38** | 290 | 45.9% |
| 769 | **7** | 259 | 48.4% |

纵向：统计卡 2 列 × 88px + 12px 间距 = **188px**，再加 tab 头/告警条/下边距约 260–300px 在布局前被吃掉。

**结论**：1024 宽（平板横屏）内容区仅 **262px**，侧栏+统计+TOC 合计占用约 68% 宽度；834 宽仅 **72px** 基本不可编辑；769–900 宽实质不可用。

### 2.3 问题清单（按严重度）

- **H1（高）PC 壳平板宽度下笔记本内容区塌缩**：`NotebookView.vue` 无 769–1280 中宽断点 + 侧栏 280 固定 + TOC 240 固定。
- **M1（中）TOC 每次打开笔记强制展开**：`beginOpenNote` 里 `tocVisible.value = true`（:1695），即使上一条已手动折叠，切笔记又吃掉 240px。
- **M2（中）wangEditor 工具栏窄编辑器横向溢出被裁切**：`NoteRichEditor.vue:1028-1033` 工具栏 `flex-wrap:nowrap; width:max-content`，外层 `.notebook-editor__content` `overflow:hidden`；编辑器 ≤300px 时按钮被右侧裁掉且无横向滚动。
- **L1（低）编辑器头部 <600px 拥挤**：`notebook-editor__title-row`/`__actions-col` 无换行断点。
- **L2（低）统计卡 2 列占 188px 纵向**：`≤1100` 无收窄为矮行的断点。
- **L3（低）mobile-v2 `.folder-grid {repeat(3,1fr)}` 固定 3 列**：375px 每卡 107px、1366px 每卡 438px。
- **L4（低）`mobile-v2-app` 无 max-width**：iPad Pro 横屏 1366px 行宽过长。

**通过项**：PC 回收站视图（1200/760 有 3→2→1 列断点）、PC 待办视图（≤1100 看板降单列）、v2 搜索/详情、旧 v1、前端构建。

## 3. 平板布局问题：根因（三层叠加）

1. **壳层是二分模型（pc/mobile），阈值 768px 是手机线**：iPad Pro 11"（834）、iPad Air（820）、主流安卓平板竖屏（800–900）全部 >768 → 落 PC 壳。
2. **PC 三栏是固定宽度**：`.notebook-sidebar{width:280px;flex-shrink:0}` + `.notebook-toc{width:240px;flex-shrink:0}`，编辑器 `flex:1` 吃剩余。`NotebookView` 里唯一的响应式只有统计卡在 1200/640 断点折叠，**三栏本体零适配**（640 断点在 PC 壳内甚至是死代码）。
3. **没有第三态「tablet」**：mobile v1/v2 是按 360–430px 手机优化的，把平板强行丢进 mobile 壳也只是手机拉大。

**壳层判定边界情况**（老杨补充）：
- `app-shell.js` 与 `deviceShell.ts` 的 UA 判定**不完全一致**（后者多了 `userAgentData?.mobile`）→ 个别设备先 pc 后 mobile 闪现（R10）。
- 桌面窗口跨 768px 会整页 `location.reload()` 反复切换；恰好 768px 一像素之差是两种完全不同的壳。

## 4. 调研：解决方案清单与推荐（小吴）

### 候选方案

| 方案 | 描述 | 结论 |
|---|---|---|
| **A（推荐·主体）** | 不动壳层二分，在 `NotebookView.vue` 组件内做响应式平板档：≤1200 侧栏缩 220px + TOC 默认折叠为浮动按钮；≤1024 左侧树改 off-canvas 抽屉；触发 `@media` 或 container query | ✅ 改动局部、对移动端/桌面零回归 |
| B | 把 `MOBILE_MAX_WIDTH` 抬到 1024，平板统一进 mobile-v2 | ❌ mobile-v2 详情**只读无编辑**，功能回归，排除 |
| C | 新增第三套「平板壳层」（main_tablet + 独立路由） | ❌ 工作量最大、三套视图并行维护，排除 |
| D（辅助） | container queries + `clamp()` + `repeat(auto-fit,minmax())` | ✅ 与 A 配套，减少硬断点 |
| E（收尾） | 统计卡 el-row/el-col 栅格化或补平板断点，height:88px 改 min-height | ✅ 小改，改善纵向空间 |

### 推荐组合

**A（主体）+ D（辅助）+ E（收尾）**。理由：对移动/PC 零回归、改动面最小、符合业界「sidebar 收起为抽屉/icon rail + 内容最大化」最佳实践；断点锚点 1200/1024 即 Element Plus `lg/md` 与 Tailwind `xl/lg` 标准。

## 5. 前端代码修改方案（小美定稿，经老杨审核）

### 5.1 总览

- **目标**：解决平板/窄窗（769–1200px，PC 壳内）三栏固定宽塌缩，对桌面 ≥1200 与 mobile-v2 ≤768 **零回归**。
- **范围**：平板布局（H1/M1/M2）+ 低优先（L1/L2/L3/L4）。**不做**：后端、壳层二分（`MOBILE_MAX_WIDTH=768` 不动）、mobile v1/v2 重构。
- **核心思路**：组件内响应式（`@media` + `matchMedia` + 复用既有 `.notebook-toc-expand` 浮动按钮）；侧栏用**原位抽屉**（`position:absolute` 覆盖），不新增第三套壳层。

### 5.2 改动清单

**P0-1（H1 主修复）：NotebookView 加平板中宽断点 + TOC 默认折叠 + 侧栏抽屉**
- 文件：`admin-web/src/utils/deviceShell.ts`（新增常量）、`admin-web/src/views/NotebookView.vue`（:706、:1695、模板 :81、样式末尾）。
- `deviceShell.ts` 新增导出（纯增量，不影响既有逻辑）：
  ```ts
  /** 平板中宽档（PC 壳内响应式上限，与 MOBILE_MAX_WIDTH=768 无耦合） */
  export const TABLET_MAX_WIDTH = 1200
  /** 平板窄档：左侧树改为抽屉 */
  export const TABLET_COMPACT_MAX_WIDTH = 1024
  ```
- `NotebookView.vue` 新增两个 `matchMedia` 状态，TOC/侧栏初始值随档位：
  ```ts
  const isTabletRange = ref(/* matchMedia(max-width:1200px) */)
  const isCompactRange = ref(/* matchMedia(max-width:1024px) */)
  const tocVisible = ref(!isTabletRange.value)      // 平板档默认折叠
  const sidebarVisible = ref(!isCompactRange.value) // 窄档默认收起
  // onMounted 挂 change 监听 / onBeforeUnmount 移除（只改 ref，绝不 location.reload）
  ```
- `beginOpenNote`（:1695）改为：`if (!isTabletRange.value) tocVisible.value = true; if (isCompactRange.value) sidebarVisible.value = false`（**统一收抽屉，覆盖树点击/新建/粘贴全部调用点**）。
- 模板：`.notebook-layout` 加侧栏开关按钮（`v-if="isCompactRange && !sidebarVisible"`）、遮罩（`v-if="isCompactRange && sidebarVisible"` @click 收起）、`aside` 绑定 `is-offcanvas/is-collapsed`。
- 样式（`@media(max-width:1024px)`）：`.notebook-sidebar{position:absolute; inset:0 auto 0 0; z-index:40; width:min(300px,82vw); box-shadow; transition; &.is-collapsed{transform:translateX(-105%)}}`；遮罩 `position:absolute;inset:0;z-index:39;background:rgb(0 0 0/32%)`；开关按钮定位左上角。

**P0-2（M2）：NoteRichEditor 工具栏窄屏裁切**
- 文件：`views/notebook/NoteRichEditor.vue`（:1028-1033）。
- `.w-e-toolbar`：`flex-wrap:nowrap → wrap`；`width:max-content → 100%`；`min-width:0`；**保留 `overflow:visible`**（wangEditor 下拉依赖；不能用 `overflow-x:auto`，一轴 auto 会把另一轴 visible 计算为 auto 从而裁掉下拉）。

**P0-3（L2 / 方案 E）：统计卡压缩**
- 文件：`NotebookView.vue`（:2135-2141、:3209-3219）。
- `.notebook-stats`：`repeat(4,...)` + 两条旧 media 替换为 `repeat(auto-fit, minmax(200px,1fr))`（删 1200 两列 / 640 一列，640 是 PC 壳死代码）；卡片 `height:88px → min-height:88px`；`@media(max-width:1200px)` 内压到 `min-height:64px`、图标缩小。

**P1-1（L1）：编辑器头部窄屏换行**
- 文件：`NotebookView.vue`（:2685-2704）。`@media(max-width:1200px)`：`__title-row{flex-wrap:wrap;gap:8px}`；`__actions-col{flex-direction:row;flex-wrap:wrap;width:100%}`。

**P2-1（可选）**：中宽档侧栏 `clamp(220px,26vw,280px)` —— **老杨建议砍掉**（1200–1025 段 280px 不挤，编辑器 ≥650px，收益极低徒增回归面）。

**P2-2（L3）**：mobile-v2 `.folder-grid → repeat(auto-fill,minmax(140px,1fr))`（`V2NotebookView.vue:278`、`V2NoteFolderView.vue:173`）。对 ≤768 有可见改动（手机 3→2 列），**独立小提交**便于回滚。

**P2-3（L4，有条件）**：`mobile-v2.scss` `@media(min-width:1025px){.mobile-v2-app{max-width:1024px;margin:0 auto}}`。**条件**：需同步确认/设置 html/body 背景色，避免居中后两侧露灰边。

### 5.3 断点策略（定稿：1200 / 1024 两档）

| 档位 | 视口宽 | 触发行为 |
|---|---|---|
| 桌面 | >1200 | 现状：TOC 展开、侧栏 280 固定、统计 4 列；**全部改动短路** |
| 平板中宽 | 769–1200 | TOC 默认折叠为浮动按钮（可手动展开）；统计 auto-fit 压矮；编辑器头部可换行 |

### 5.4 老杨审核结论（有条件批准）

**整体裁决**：**有条件批准**，方案成立可执行。理由：范围克制、技术选型与现状吻合（layout 已有 `position:relative`、`tocVisible`/浮动按钮可复用）、行号引用全部属实。

**四个落地修正**：
1. **去掉** `@media(max-width:1024px){.notebook-layout{overflow:visible}}` 改动，保持默认 `overflow:hidden`（祖先链 `.notebook-tabs-wrap/.el-tabs__content/.notebook-tab-all` 全 `overflow:hidden`，抽屉开启态在 translateX(0) 内不受裁剪，关闭滑出被面板左缘裁切是标准抽屉视觉）。
